## What the merge brought in, on top of origin/main

The 26 commits of `ampere-3060-port` plus five from today. In one paragraph each:

- **The Ampere port**: VBIOS falcon boot (FWSEC-FRTS out of the card's ROM, booter_load over SEC2), QMD v3 descriptors,
  MMU v2 page tables, the Ampere engine classes, `nv_regs.h` generated for both architectures, the register sequencer
  GSP-RM asks the driver to run, and `TINYCC_ARCH=sm_86` for the device compile. The recorded 3060 boot
  (`traces/3060-boot`) replays with 0 divergences, as does the 5090's.
- **The card is left cold** (NVIDIA's unload: notice, halt, FWSEC-SB, booter_unload, region down; 0.3 s) so the next
  open never resets a warm card. `TINYNV_UNLOAD=0` keeps the old idle-warm behaviour.
- **The window loss and the retry.** On this card, a few seconds into any boot after the first in an enumeration, the
  PCI configuration can be cleared under the running firmware: command register and all six BARs to zero, card still on
  the bus, macOS silent. It is a per-boot event, hardware-side as far as anything can tell (no build or registry setting
  changes the rate; it got markedly worse after the 27B runs heated the enclosure), and the driver now survives it:
  BARs and command register are snapshotted at open and written back the moment the quarter-second watch sees them go;
  if the start-up notice still has not come ten seconds later, the boot is given up, the card reset through the dext
  and its configuration put back (`tinynv_dev_reset_cold`), and the firmware booted again, up to three attempts. A
  lost attempt costs about twelve seconds. `QUIESCE=1` on every step is the protocol here, not an option.
- **Merge decisions**: origin's barrier/invalidate knobs on the two-generation descriptor pairs; origin's tinycc with
  the explicit SDK and a non-root arm64 container; per-architecture objects and archives; origin's graph define in the
  archive build (the sm_86 archive here was built *without* graphs - rebuild it with `ARCH=sm_86 sh
  cuda-shim/build/build-ggml-cuda.sh` to get them); origin's firmware-carveout check passes on the Ampere layout.
- **Tools**: the recovery tools know an Ampere card; `NGL=`/`NGLD=`/`BENCH_ARGS=` on the runner; `tools/agentbench.sh`
  and `tools/agent-replay.{sh,py}` for the coding-agent benchmark (depth sweep and ten-turn cache-reuse replay).

## The window loss, resolved (15:45)

What clears the configuration is the PCIe link at Gen4. On a fresh 16 GT/s enumeration with the firmware allowed
Gen4, every boot lost the card's configuration on every attempt (23 losses in 18 tries), and the loss lines showed the
link flapping between Gen4 and Gen1 the whole time; each drop clears the endpoint's configuration while the GPU core
keeps running, and macOS logs nothing. With the firmware capped at Gen3 (`RMPcieLinkSpeed` with Gen4 and Gen5 disabled
and LOCK_AT_LOAD) the same card came up first try, three of three, starting from that Gen4 link. The link idles down
to Gen1 after every unload, and a boot that asks for Gen3 from that Gen1 link gets it: the firmware retrains the link
up to 8 GT/s a few seconds into the boot and it stays there for the rest of the process (sampled from the host every
few seconds; 189 of 189 samples through the sixteen-minute sweep), and the gate runs in 21 s instead of 37. So the
driver's default is `TINYNV_PCIE_LINK_SPEED=auto` = Gen3, always (`1621873`; `e23369c` had "the current generation or
Gen3, whichever is lower", which left an idle Gen1 link at Gen1). A Thunderbolt tunnel carries no more than a Gen3 x4
link's worth of PCIe, so nothing is given up. `QUIESCE=1` stays the protocol on every step: its reset retrains the
link to Gen1, and the next boot brings it back to Gen3, so it costs the ten seconds it always did and nothing else.
The retry stays as insurance. The window-loss watch in `gsp.c` has not fired since the cap went in.
