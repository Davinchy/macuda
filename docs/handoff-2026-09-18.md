## What this session investigated (driver decode-parity, prompted by "some benchmarks hit parity, some don't")

1. **Runqueue-split idea (`NVOS04_FLAGS_GROUP_CHANNEL_RUNQUEUE`) — closed, root-caused, not a dead end from
   confusion but from hardware fact.** Tried putting the copy channel on a second TSG runqueue to avoid the
   compute↔copy runlist-switch stall at every MoE decode token boundary. Crashed once, hung once (the hang
   caused a real DART fault needing a physical replug — do not repeat this specific test). Root cause, found via
   a read-only print of data the driver already fetches every boot: GR0 (compute) has 2 PBDMAs, every copy
   engine (CE0–CE7) has exactly 1. The flag asked for a PBDMA index the copy engine doesn't have — undefined
   behavior nothing validates. Also settled the mechanism: the flag is for two channels of the *same* engine
   feeding concurrently, not a compute↔copy cross-engine mechanism — it was never going to solve this problem
   even working correctly. Kept in the tree, off by default, as documented evidence (`ecafc8c`).
2. **README benchmark table was stale, not the driver underperforming.** Re-verified against a clean gate build:
   dense 27B tg128 65.3→67.8 tok/s, MoE 35B-A3B tg128 134.3→162.6 tok/s (55%→66% of native), Z-Image-Turbo
   10.16s→9.67s (already near parity). Confirmed twice independently. Fixed in `README.md` (`2f5d4b9`).
3. **MoE per-token descriptor-delta measurement and a delta-delivery implementation attempt — infrastructure
   safe, real win not yet achieved.** Measured directly on hardware that an individual launch's descriptor
   content is ~97% unchanged token to token (small, predictable fixed-stride KV-cache offset/address counters,
   never expert-routing-dependent addresses). Built `TINYNV_DELTA_DELIVERY` (off by default) to patch only the
   changed bytes via the existing `TINYNV_INLINE_UPLOAD` path instead of a full copy-engine job. **Correctness
   fully validated: byte-identical greedy decode output on dense and MoE models with the flag on, op-verify
   450/450.** But it's currently a no-op in practice: a real flush accumulates many launches (~213KB in one
   measured case) before delivering, and one min-max envelope over that much content is ~100% "different" the
   moment even one byte differs near each end — confirmed on hardware with `TINYNV_DELTA_VERBOSE=1`. The 2.7%
   figure was real but measured at the wrong granularity (per-launch, not per-flush). Landed safely anyway
   (`26b0562`, `a4f9010`) with the mistake documented in the code so it isn't relearned.

## The scoped next step, not yet started

Diff each launch's own small sub-block *individually* within a flush (bounds already available via `ex->chain[]`
— currently tracks `.va`/`.host` per launch, would need a `.len` added), rather than one envelope over the whole
flush. Only take the fast path when *every* launch in a flush is individually small-diff, patching each with its
own inline upload; fall back to today's full bulk copy otherwise — a clean either/or per flush, no risk of
double-delivering the same bytes. This is the real fix; the current commits are safe groundwork for it, not the
fix itself.
