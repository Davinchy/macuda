## What this session did: finished the scoped next step from the 09-18 handoff, found the next one

The 09-18 handoff's "scoped next step, not yet started" was per-launch descriptor diffing (diff each launch's own
sub-block individually within a flush, instead of one envelope over the whole flush). This session implemented,
crashed it once on real hardware, fixed it, then found and partly fixed a second problem, and ends with a third
one clearly scoped but not started. In order:

1. **Implemented per-launch diffing** (`c728085`) — `chain[]` gained a `.len` field (QMD slot + that launch's own
   cbuf0 size, which varies per kernel), and `tinynv_exec_flush` diffs each launch's own span individually against
   `last_delivered` instead of one min-max envelope over the whole flush. All-or-nothing per flush: every launch's
   diff has to fit before anything is committed, or the flush falls through to the existing full-copy path
   unchanged — no risk of double-delivering bytes.

2. **Crashed on hardware, root-caused, fixed** (`51a1011`) — first real hardware run (`TINYNV_DELTA_DELIVERY=1
   TINYNV_INLINE_PEND=128`, Qwen3.8-27B greedy decode) aborted: `tinycudart` error, "an inline upload is a whole
   number of dwords, not 1542 bytes". The byte-precise diff scan produced spans with no alignment guarantee, and
   `tinynv_cmd_inline_upload` requires both the length and destination to be 4-byte aligned (`submit.c:65-67`).
   Fixed by widening each launch's diff bounds to the nearest dword on both sides — safe because a launch's own
   span is itself 256-byte aligned with a 256-byte-rounded length, so widening can never cross into a neighbour's
   span. Worth noting: the single-envelope version this replaced (`a4f9010`) had the identical latent bug — it
   just never reached the inline-upload call often enough to hit it, because the whole-flush envelope almost
   always read as too big to fit and fell back first. Re-validated: op-verify 450/450 at three depths,
   byte-identical decode, no crash, including at the setting that crashed before.

3. **Found and partly fixed a real bottleneck** (`b76c16a`) — even fixed, the mechanism was landing on only 5 of
   1223 flushes in a 96-token decode. Root cause: delta patches were queued through the same `inline_pend` list
   `TINYNV_INLINE_UPLOAD` uses for its own per-launch copies (default budget: 16 entries / 8 KB), and that shared
   list was mostly spent before delta delivery's own check ever ran. Fixed by writing delta patches directly into
   the chain's own delivery batch after `batch_begin()` (reserving their own room in `want_dwords`) instead of
   queuing them — the two mechanisms no longer compete for the same held list. Also added a separate aggregate cap,
   `TINYNV_DELTA_AGGREGATE_MAX` (64 KB, explicitly marked provisional in its own comment — not swept), since the
   old `TINYNV_INLINE_MAX` (4096 bytes) prices one small copy against the copy engine, not a whole flush of patches
   against the ~800 µs full-envelope fallback they actually compete with.

   **Still only 5 of 1223 flushes fire, and this session found out why — that's the real finding, not the two
   fixes above.** A one-shot diagnostic (gated behind `TINYNV_DELTA_VERBOSE`, first three flushes only, still in
   the tree) showed: nearly every one of a chain's 128 launches carries *some* genuine per-token change, not just
   the one or two that looked special before the budget was untangled. Span widths are consistently ~1400-1800
   bytes, but the bytes that actually differ inside each span are only ~40-240 of them — 3-15%, usually ~10-13%.
   **The per-launch min-max envelope is overestimating by roughly 7-10x** — the exact same shape of bug that
   motivated per-launch diffing over the original whole-flush envelope, recurring one level down. Extrapolated
   across a full 128-launch chain, genuine content is probably ~20-25 KB against the ~185 KB the envelope currently
   reports — which is why raising the aggregate cap (tried 16 KB, then 64 KB) mostly just moved the miss point
   rather than fixing anything: the envelope is the binding constraint now, not the budget.

   Correctness held through all of it: op-verify 450/450 at chain depths 32/64/128, 96-token greedy decode
   byte-identical to the reference text, across every cap value tried, no crash.

## The scoped next step: sub-launch diffing, not yet started

Diff **within** each launch's own span too, not just per-launch. Same pattern as this file's whole history so far
— whole-flush envelope, then per-launch envelope, then untangling the delivery budget, now sub-launch envelope is
where the same overestimate keeps showing up.

**What it means concretely.** Right now, for each launch, `tinynv_exec_flush`'s check pass finds one `(dlo, dhi)` —
the first and last differing byte in that launch's `[lo, hi)` span — and treats everything between them as dirty.
Instead, find the actual differing *runs* within that span (a simple pass: track a run while consecutive bytes
differ, close it when they stop, merge two nearby runs if the gap between them is small enough that a second
`tinynv_cmd_inline_upload` call costs more than the merge would — each call is a fixed 8-dword overhead
(`TINYNV_INLINE_DWORDS`), so gaps under roughly that many bytes are cheaper to include than to split around).

**What's reusable, what's new:**
- Reusable as-is: the dword-alignment widening (`dlo &= ~3; dhi = (dhi+3) & ~3`), the all-or-nothing per-flush
  commit discipline, the direct-into-`batch_begin`'s-batch delivery mechanism from `b76c16a`, the aggregate cap
  concept (though its value will need re-tuning once sub-spans are real — it was sized against the *current*
  overestimating envelope).
- New: a bounded per-launch sub-span list (the current `plo[]`/`phi[]` are one `uint64_t` per launch;
  sub-launch diffing needs several per launch — a flat `{lo, hi}` list across the whole flush, capped at some
  total count, is probably simpler than a 2D per-launch array). A cap on how many sub-spans one launch may
  produce before that launch (and so the whole flush, same all-or-nothing rule) is treated as "did not fit" and
  falls back — this is the new failure mode to reason about carefully, on top of the existing per-span and
  aggregate-byte caps.
- The gap-merge threshold is a new tunable with no measured default yet — start from the 8-dword-per-call
  arithmetic above as a first estimate, expect to actually sweep it against hardware data the way `TINYNV_CHAIN_DEPTH`
  and `TINYNV_INLINE_PEND` were, not just reason it out.

**Validation, same discipline as every lever in this file:** op-verify 450/450 at chain depths 32/64/128,
byte-identical greedy decode against the reference text, `TINYNV_DELTA_VERBOSE` re-checked to confirm the new
sub-span accounting actually engages and the genuine-vs-envelope gap actually closes (re-run the same diagnostic
this session added — it's still in the tree, gated behind the env var, first three flushes only). Needs the card;

## What this session did: built the scoped next step, offline only

Sub-launch diffing, exactly as scoped above, landed as `86805a2`. The commit message has the full account; the
short version: `tinynv_delta_runs` finds the runs of *dwords* that differ within each launch's span (no more byte

   Each flush's runs still carried ~70 KB of a ~200 KB envelope; ~90 KB of pushbuffer a flush is ~380 µs of
   processor writes across the link at the ~4.2 µs/KB of §4d, on every flush, against the one boundary handoff
   (~350 µs a token) it removes. The gap sweep (`step16-*`: gap 0/8/32/128/512) showed the cost tracks bytes, not
   patch count - 298 to 1504 patches a flush at ~100 KB all read 83-85 t/s - so no cheaper per-patch primitive would
   have helped. §4f's "why there is no fifth lever" arithmetic stood exactly as written.
2. **Why 35% and not the "2.7% a token" the lever was built on.** The ring rewinds at a chain boundary, so what was
   last delivered at a launch's address is a *different* launch of the same kernel (another layer's pointers and
   strides). The 2.7% (`26b0562`) was a launch-to-launch measurement read as token-to-token.
3. **`TINYNV_DELTA_REWIND=1`** (`74fcfe7`): at the first launch after a standstill the descriptor region is declared

   launch k of the last one did. Footprint 85 KB -> 6.6 KB a flush (prediction on the record in the commit: under 15).

4. **`TINYNV_TAIL_RELEASE=1`** (an existing knob: only the chain's tail releases the timeline) removes that patch:
