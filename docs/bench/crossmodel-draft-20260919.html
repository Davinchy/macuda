Cross-model study · measured 19–20 September 2026

Six models. One inference question.

How does the benefit of CUDA prefill change with active parameter count? This study extends the disaggregated-inference experiments to six mixture-of-experts models, spanning 3B to 39B active parameters. Each model is evaluated on the RTX 5090 and the Mac's GPU at four prompt lengths.

Active parameters are reported in billions (B), not bytes of model data. KV cache estimates use model-header dimensions and an assumed two bytes per cached value: layers × KV heads × (key dimension + value dimension) × 2. Architecture-specific layouts may differ; the DeepSeek estimate requires runtime confirmation. All model files are stored on the same external drive.

Test protocol

Each model is scheduled for prefill on both backends: the RTX 5090 through macuda over Thunderbolt, and the Mac's GPU through Metal. Prompt lengths are 12,000, 24,000, 26,000 and 48,000 tokens. 24,000 and 26,000 straddle the 24,576-token ubatch boundary, where expert data must be transferred again. The 12,000- and 48,000-token runs extend the context-length comparison.

methodMatch token counts across models and token IDs across backends. Each model tokenizes the same source text with its own tokenizer, then the token sequence is truncated to the target length. CUDA and Metal receive identical token IDs for that model. This keeps each run on the intended side of the ubatch boundary, even though models tokenize the text differently.

The prompt cache is cleared between lengths to prevent shared-prefix reuse from inflating prefill results. Every model uses all experts in host memory (--n-cpu-moe n_layer), matching the configuration used to fit the initial cost model. Per-model residency tuning is outside this study's scope.

Hypotheses and interpretation limits

These were written down before the measurements and are unedited apart from wording. Where one turned out wrong it is marked wrong below rather than quietly revised.

hypothesis 1Higher active-parameter counts produce larger prefill gains. The proposed ordering places Mixtral at the high end and Qwen3-Coder-Next at the low end. A flat or reversed ordering would challenge that explanation. Differences in transfer volume, quantisation and kernels must also be considered before attributing the result to active parameters alone.
hypothesis 2Relative prefill gains increase with prompt length. The Qwen3-Coder-Next measurements increased from 2.35× near 24k tokens to 5.55× near 48k. The sweep tests whether that direction holds for the other models. Any model with a lower speedup at 48k than at 24k would refute the universal claim.
hypothesis 3Crossing the ubatch boundary adds another expert transfer. The 26,000-token run should take longer than a smooth compute-only extrapolation from 24,000 tokens would predict. The expected additional cost depends on each model's expert data. A smooth transition would challenge this mechanism for that model.
study limitationKV-cache effects are not isolated by this model set. Estimated cache sizes and active-parameter counts vary together, while attention architectures and quantisation also differ. Context sweeps can describe each model's behaviour, but cannot by themselves assign a cause. An earlier hypothesis linked cache growth to displaced resident experts; the all-experts-on-host protocol does not directly test that mechanism.
open questionConfirm DeepSeek's runtime cache layout. The 86 KB/token estimate assumes an expanded cache. A compressed 512-wide latent plus rotary-position data would give an estimate nearer 48 KB/token. The server's reported KV-buffer allocation at a known context length is needed to resolve the difference.

Every model ran with every expert in host memory — the one configuration identical across all six, which makes the comparison clean and makes each number a floor: roughly 20 GiB of card memory sat unused that a tuned deployment would fill with resident experts.

confirmedActive parameters are the lever, and the ordering is monotonic. Rank the six by the bytes a token actually touches — 3.4, 3.9, 5.8, 8.5, 9.8, 21.3 GiB — and the 24k column rises with it. Total size predicts nothing: the largest model in the set sits near the bottom and the smallest sits beside it. DeepSeek-V4-Flash is the one exception, and it is instructive rather than awkward: its MLA attention keeps Metal at a flat ~178 tok/s out to 48k where every other model collapses, and since the card's advantage is manufactured by Metal's degradation, an architecture that protects Metal takes the advantage away.
confirmedThe second-ubatch cost is the expert stream, measured directly. Going from 24,000 to 26,000 tokens adds 2,000 tokens of work and crosses one ubatch boundary. Across six models whose expert sets span 43.7 to 83.6 GiB, that step costs 6.9 to 16.1 s and tracks the bytes linearly — an implied 4.9 to 6.4 GiB/s over the link. No curve fitting: two measurements per model. The implied rate falls as the model grows, which is what page-cache pressure would look like — at 83.6 GiB of experts the host can no longer hold the whole set in RAM alongside everything else, so part of each stream comes off the disk. Untested.

A three-parameter fit of ⌈tokens ÷ 24,576⌉ × transfer + tokens ÷ rate + fixed was attempted per model and is not reported: on four points whose first is a cold-mapping outlier it returned residuals of 3.5–6.6 s and, for two models, an infinite marginal rate. The fit was absorbing the cold point into its constant. The direct two-point step above measures the same quantity without that freedom.

The 12k column is cold, not slow: it is the first prefill after each model loads, and it faults the entire expert set in from disk. Later points in the same session are warm. It is kept because it is a fair measure of what the first request after a load costs, which a user does feel — but it is not a point on the context curve.

Stability monitoring

The observation window opens when the sweep takes the card and the figure reported is elapsed time under load — not the driver extension's total process lifetime. An idle card stays "up" indefinitely and that number carries no information; what the sweep is in a position to measure is how long the device keeps working while being worked. The extension's process lifetime remains the invalidating signal: macOS restarts that process when the device is re-enumerated, so an unbroken instance across the window is the claim that the card never left the bus under load. It must still be interpreted alongside device-enumeration and error logs. The counters below await a completed window.

baseline event, resolvedThe driver instance carrying this sweep began at 21:45:40 on 19 September, while the card was idle. Preflight refused on the changed instance, as designed, and it was cleared by hand before the sweep — at which point the cause was not established, and this note said so. It is now established and it was not the card: the host itself rebooted at 21:45:12, brought down by a faulty USB device, and the driver extension came up 28 seconds later. kern.boottime and the extension's start time agree to the second. The link never dropped below 16 GT/s ×4, no DART error data was latched, and nothing crossed the Thunderbolt bus abnormally. The instance's age is therefore a fact about host uptime, not about the card — which is why the figure above is measured from the sweep's first card step instead.
