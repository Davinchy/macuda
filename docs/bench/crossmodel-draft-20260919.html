Six models, one card

The disaggregation page argues that active parameters, not total size, decide whether a model belongs on this path — that the card's advantage is largest exactly where an Apple GPU is worst. That argument was made from one model and a pile of published figures. These six test it directly: 3B to 39B active parameters at roughly the same total size, both halves, same prompts.

If active parameters are what matter, this is where the advantage is largest; if the KV cache is what matters, this is where long context hurts most. It is in the set to be pulled in both directions at once.

KV per token is layers × KV heads × (key + value) × 2 bytes, from each header. Active is the GiB a token actually touches — everything that is not an expert, plus the routed fraction of the experts — read from each file's own header, not from the model card. KV bytes a token are computed from the header the same way: layers × KV heads × (key + value) × 2. Every file lives on one external drive so that load time is a property of the rig and not of which disk a model happened to be on.

What is actually run

Each model is prefilled on both halves — the card through this driver over Thunderbolt, and the Mac's own GPU through the kit's Metal build — at 12,000, 24,000, 26,000 and 48,000 tokens. 24,000 and 26,000 straddle the 24,576-token ubatch boundary, where the expert stream is paid a second time; 12,000 and 48,000 give the context curve its ends.

methodThe lengths are token counts, not prompt files. The same 267 KB of text is 71,504 tokens to one tokenizer and rather fewer to another, so "the same prompt" would land on different sides of the ubatch boundary for different models and the step would become an artefact of vocabulary. Each server tokenizes one base text with its own tokenizer and the ids are sliced to exactly the length asked for.

Two more things the rig does on purpose. The slot is erased between lengths, because these prompts are prefixes of one text and a cache hit would be recorded as an impossibly fast prefill. And every model runs with every expert in host memory (--n-cpu-moe n_layer): that is the configuration the cost model's constants were fitted on, and the only one identical across models — tuning residency per model would measure the tuning rather than the model.

Predictions, before the data

prediction1. The advantage rises with active parameters. The card's fixed cost is the expert stream, in seconds, and it does not care how much arithmetic a token needs; Metal's cost is all arithmetic. So Mixtral at 39B active should show the largest advantage in the set and Coder-Next at 3B the smallest, with the others ordered between them. Refutation: if the ordering is flat or inverted, the page's central claim is wrong and total size or something else is doing the work.
prediction2. The advantage rises with context, for every model. Measured on one model on 19 September: 2.35× at 24k to 5.55× at 48k, because Metal's prefill rate collapses from 673 to 304 tok/s while the card's holds. Refutation: a model whose advantage falls between 24k and 48k. Mixtral is the most likely place to see one, because its 229 KB/token cache is the one that can displace enough resident weight to bite back.
prediction3. The ubatch step is real on models it was not found on. Going from 24,000 to 26,000 tokens — 2,000 more tokens of work — should cost each model roughly its own expert stream again, several seconds, not the fraction of a second the extra tokens are worth. Refutation: a smooth slope through that boundary on any model.
prediction4. The KV axis shows up inside each model's curve, not across the set. This one was rewritten before the run, and the reason is worth keeping: the set was assembled believing DeepSeek-V4-Flash's MLA cache was about 1 KB a token against Mixtral's 229. Read out of the headers it is 86 KB against 224 — a factor of 2.6, not a hundred, and the six models' KV sizes turn out to be correlated with their active parameters (72 KB at 5.1B active, 224 KB at 39B). A cross-model comparison therefore cannot separate the two axes at all. What can is each model's own curve from 12k to 48k: active parameters set how high it sits, the KV cache sets how much it sags, because the cache is what displaces resident experts. So the prediction is that the ordering of the six holds at every length, while Mixtral and Scout — 224 and 192 KB — lose more of their advantage between 24k and 48k than gpt-oss and DeepSeek do at 72 and 86.
open question the run answersWhether llama.cpp caches DeepSeek's MLA latent compressed or expanded. The header arithmetic that gives 86 KB a token assumes expanded; if the cache is the 512-wide latent plus rope instead, it is nearer 48. The server prints its own KV buffer size at a known context, so the run settles it rather than leaving it to the header.

How long does the card stay up?

A long sweep is also an endurance test, so this one is timed. The clock is the driver extension instance's lifetime: macOS restarts that process when the card is re-enumerated — a replug, a sleep/wake, a bus reset — so "same instance, same start time" is exactly the claim that the card has not gone away, and it is the same signal preflight refuses on.

Sampled every five minutes by tools/card-uptime.sh, which is deliberately read-only — ps, ioreg and the lock file, nothing that opens the device. A sampler that had to open the card would be measuring its own interference, and on this stack a second opener is how you get two drivers on one card.

honest about the clock's startThe clock starts at 21:45:40 on 19 September, which is when the current driver instance began — while the card was idle, seventeen minutes after the last run of the evening finished. The link stayed up at 16 GT/s ×4 throughout and no DART error data was latched, so nothing was damaged, but the instance did restart and the cause is not established. Preflight refused on it, as designed, and it was cleared by hand before this sweep began. An uptime figure that quietly began after a restart nobody mentioned would not be worth printing.
