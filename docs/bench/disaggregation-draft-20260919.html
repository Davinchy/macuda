Prefill on the card, decode on the Mac

A 50 GB model does not fit the card's 32 GB. It can still use the card for the half it is good at: the card processes the prompt while the experts stream across Thunderbolt, then the conversation's state is handed to the Mac's own GPU to generate from. Here is what that is actually worth.

The headline, and it is the opposite of what was expected

measuredLong context makes this more valuable, not less. The premise under test was that a longer prompt would erode the advantage. It does the reverse: the advantage more than doubles between a 24k prompt and a 49k one, because the Mac's prefill degrades far faster with context than the card's does.

Qwen3-Coder-Next 80B-A3B, 46.2 GB, every expert on the host. Card half through this driver on the 5090 over Thunderbolt; Mac half on Apple's own GPU, same model file, same prompts, prefill only.

The cost model this project had been using assumed the Mac prefills at a constant 660 tok/s, because that is what it measured once, at 24k. It holds there — 673 measured — and then falls apart: by 49k the Mac is down to 304 tok/s. Prompt processing is compute-bound, and an Apple GPU of this generation has no dedicated matrix hardware, so the quadratic part of attention hurts it much more than it hurts the card.

overturnedPredicted: the advantage decays with context, from 4.2× at 24k to 3.2× at 192k, because the KV cache displaces resident experts. The KV displacement is real and does push the other way — but it is swamped several times over by the Mac's own degradation. Modelling one side and assuming the other is what produced a confident number with the sign wrong.

The assumption everything rested on, finally tested

The card's cost has a ceiling function in it: llama.cpp re-copies every host-resident expert for each ubatch it evaluates, so the expert stream is paid once per 24,576 tokens rather than once per prompt. Every one of the six prefills the cost model was originally fitted to sat inside a single ubatch, so this had never been observed — it had been read out of ggml's source.

measuredIt is real. Two prompts either side of one boundary, each run twice, identical both times: 23,691 tokens (one ubatch) takes 15.0 s, and 26,156 tokens (two ubatches) takes 22.0 s. Those 2,465 extra tokens are worth 0.8 s of compute. The other 6.2 s is the expert stream being paid a second time.

The card's constants, refit

measuredFour fresh prefills on the current build fit ⌈tokens ÷ 24,576⌉ × 6.21 s + tokens ÷ 3,300 + 1.65 s to within 0.10 s rms. Two of the three shipped constants were wrong: the expert stream costs 6.21 s per ubatch rather than 8.00, implying the link carries it at 7.0 GiB/s rather than 5.46; and the card's marginal prefill rate is 3,300 tok/s, not 5,150.

Choosing a model

Two properties decide whether a model belongs on this path, and the first is the one that gets misjudged.

Active parameters, not total size

measured, publishedPrefill on an Apple GPU tracks 1 ÷ active parameters almost monotonically, across both mixtures and dense models. Published llama.cpp Metal figures: a 3B-active mixture reaches 1,213 tok/s; a 5.1B-active one 737; a dense 22B, 239; a dense 70B about 85. Total parameter count barely matters — a 117B model with 5.1B active prefills roughly 8.7× faster than a dense 70B.

That is the whole argument for this path. The card's advantage is largest exactly where the Mac is worst, and the Mac is worst when many parameters are active. A mixture with few active parameters is already tolerable on the Mac and has least to gain.

Size, as a proxy for what must stream

Whatever does not fit the card's roughly 30 usable GiB streams every ubatch. Below about 30 GB there is no reason to use this path at all — the model fits the card outright, where this project measures 5.5–7.3× over the Mac, beating anything here. Above about 100 GB the model no longer fits the Mac's memory for the decode half.

cautionOne finding from upstream worth knowing before building on expert streaming: during decode, expert routing is heavily skewed, so a small resident cache catches most hits. During prefill that skew disappears and essentially every expert is touched. A design that assumes routing skew will work for decode and fail for prefill. This project's path streams every expert per ubatch and so never depended on the skew, but a cleverer one would.

Screening a model before downloading it

tools/disagg-screen.py reads a GGUF's header — a few megabytes at the front of the file, no weights mapped, no card involved — and reports what must stream, the predicted advantage, and the prompt length below which the Mac alone wins. It refuses to score a dense model larger than the card, because expert streaming is the mechanism and a dense model has no experts.

Its context sweep still carries the overturned assumption above and reads low at long context. The measured direction is the one on this page.
