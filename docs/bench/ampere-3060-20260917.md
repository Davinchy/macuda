# RTX 3060 (GA106, sm_86) on an M3 Max over Thunderbolt — first numbers

2026-09-17. ASUS RTX 3060 12 GB, device 0x2504 rev A1, in a Razer Core X V2, on an Apple M3 Max (48 GB, macOS 27.0).
No NVIDIA driver on the Mac. Driver is `libtinynv`'s vbios/FWSEC boot path, descriptors are QMD v3, ggml-cuda built for
`sm_86` through nvcc in a container on this same Mac.

## The gate

    sh tools/nv_shim_step.sh A opverify
    450/450 tests passed        Backend CUDA0: OK        exit 0 after 20 s

Value-checked `test-backend-ops` on the card, at the driver defaults: asynchronous submission, chain depth 128, arena
in video memory, descriptors delivered by the copy engine. The same score this tree gets on a 5090.

## llama-bench, Qwen2.5-7B-Instruct Q4_K_M (4.36 GiB, 7.62 B), -ngl 99 -p 256 -n 128 -r 3

    | model                  |     size | params | backend | ngl |  test |             t/s |
    | qwen2 7B Q4_K - Medium | 4.36 GiB | 7.62 B | CUDA    |  99 | pp256 | 2106.19 ± 4.91  |
    | qwen2 7B Q4_K - Medium | 4.36 GiB | 7.62 B | CUDA    |  99 | tg128 |   65.11 ± 0.38  |

The whole model is resident on the card; nothing is streamed. Decode at 65.1 tok/s against a card with 360 GB/s of
memory bandwidth and a 4.36 GiB model is about 79% of what bandwidth alone allows, which is the number to beat rather
than a number to be pleased with.

## What is NOT established

A greedy decode was attempted immediately after and did not complete: the card dropped off the bus during the single
4168 MiB allocation that loads the model, which is the same enclosure power fault that dropped it twice while idle
earlier in the day. `llama-bench` loads the same model successfully, so this is marginal rather than broken, and it is
the enclosure rather than the driver - the signature is every register and every page-table entry reading all ones,
which is `dev.c`'s own description of a card that has fallen off.

So: the op gate is validated, the throughput numbers above are measured, and the byte-compared greedy decode that the
validation recipe in README.md §Run also asks for is still owed. It needs a power supply that holds under a 4 GB
transfer.

## What was actually wrong, and what fixed it (2026-09-19 and 2026-09-21)

The "every second boot fails" reading from 2026-09-17 was half right. What fails is any boot after the first in one
enumeration, and it is not GSP-RM going silent: a few seconds after the register sequence completes, **the card's PCI
configuration is cleared under the running firmware** - command register to zero and all six base address registers
to zero - while the card stays on the bus, config space stays readable, and macOS logs nothing. With the windows gone
every register reads all ones, page tables written through the memory window go nowhere, and GSP-RM, which is alive
and finished booting, has no bus mastering and nowhere to write its start-up notice. The proof: restoring the command
register alone made the notice arrive at once (logs/shim-opverify-20260921-094803.log), and a later process that set
the register on 2026-09-19 received the whole backlog into freed memory, which is where that day's fault record came
from. What clears the configuration is not established; the dext's own reset does not restore it, and neither does
anything but re-enumeration - unless the values are known, and they are readable while the card is good.

Three changes, all now run on the card:

- **The driver leaves the card cold**, the way NVIDIA's driver does: the unload notice, a wait for the core to park,
  FWSEC-SB, then `booter_unload` tearing the write-protected region down. Measured: 0.05 s to halt, 0.25 s to tear
  down, every run. The next open needs no reset (`TINYNV_UNLOAD=0` keeps the old behaviour).
- **The driver snapshots the six base address registers and the command register at open, and writes them back if
  it finds them cleared** while waiting for the start-up notice (dev.c tinynv_dev_restore_decode). Seen working once
  (logs/shim-opverify-20260921-095138.log: all six read back correctly); that boot then spun in a corrupted status
  queue, which is now bounded (gsp.c rpc_drain refuses a zero-length record, an out-of-range pointer, or more records
  than the ring holds).
- **QUIESCE=1 on every step is the protocol**, not an option. `nv_e3_flr.py` snapshots the configuration while it is
  valid and puts it back after its reset; the two tools that judged a 3060 "unexpected arch" and "GFW not booted" now
  know where Ampere reports its boot firmware done.

With that, five boots in one enumeration on 2026-09-21, no replug:

    10:04  opverify   450/450                                   (the first second-boot ever to pass)
    10:05  bench      qwen2 7B Q4_K_M  pp256 2112.79 ± 11.68   tg128 65.39 ± 0.14
    10:05  sd         SDXL-Turbo 4 steps 512x512  5.51 s, PNG byte-identical to the 2026-09-17 card image (sha 71fe5e05)
    10:06  simple     96 tokens greedy at 63.74 t/s, text sha 681defc9764b (logs/shim-simple-20260921-100628.txt)

Each ended with the unload line and a clean quiesce. The byte-compared greedy decode the validation recipe asks for is
therefore no longer owed; its reference text is the file named above.

Still open: what clears the configuration. `TINYNV_REGISTRY=none|nosave|nosbr` sends GSP-RM a registry table without
one or both of `RMForcePcieConfigSave` and `RMSecBusResetEnable`, the two keys that plausibly bear on it, for the next
session that sees the loss.
